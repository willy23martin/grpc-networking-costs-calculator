How SAGA affects your gRPC traffic

RPS vs. SAGA steps are different concepts. Your RPS (e.g. 1,000 req/s) measures how many logical business requests arrive per second — for example, 1,000 customers placing an order per second.

Each of those orders triggers one SAGA instance, which internally coordinates multiple microservices. Every step in that SAGA instance is a separate gRPC call to a different service:

↳Compensatable step (e.g. Reserve inventory) — can be undone if a later step fails.
Pivot step (e.g. Charge payment) — point of no return.
Retriable step (e.g. Ship order) — guaranteed to eventually succeed.

So the formula is multiplicative, not additive:

effective gRPC traffic = base RPS × steps per SAGA instance

Example: 1,000 RPS × 3 steps = 3,000 gRPC calls/sec — not 1,000 + 3,000 = 4,000. The 3 steps replace the single call; each of the 1,000 requests fans out into 3 independent calls.

🔒 Security Tactics
How security tactics affect your TCO

Security tactics impact costs in two independent dimensions — payload size and request count — depending on the mechanism involved:

Byte overhead is added to every gRPC message frame and directly increases your monthly throughput (GB/month) and therefore your data transfer cost. The calculation uses the typical value from the RFC-grounded range.

effective message size = proto size + TLS overhead + JWT header overhead

Extra requests are connection-setup messages (TLS/mTLS handshakes) or authorisation server calls (OAuth token acquisition, remote introspection) that add to your effective RPS count.

effective RPS = tactics-adjusted RPS + handshake msgs/s + token acquisition req/s + introspection req/s

Ranges shown throughout this section are based on RFC 8446 (TLS 1.3), RFC 7519 (JWT), RFC 7523 (JWT Profile for OAuth 2.0), RFC 9101 (JWT-Secured OAuth 2.0 Requests), and RFC 6749 (OAuth 2.0).

Encrypts every gRPC message using TLS 1.3 (RFC 8446). The server presents a certificate; the client verifies it against the CA. ⊕ Adds bytes to every message — the TLS record header and AEAD authentication tag wrap each gRPC frame. The TLS handshake is connection-scoped and only generates extra messages at reconnect time, not per request.

A separate attribute, client_keep_alive.seconds, caps the total lifetime of a persistent HTTP connection regardless of activity — it defaults to 3,600 seconds and is configurable from 60 to 604,800 seconds (7 days). A connection that goes quiet for 60 seconds is closed by the ALB and the next gRPC call triggers a new handshake. As a practical guide: at the 60-second default idle timeout with intermittent traffic, configure up to 60 reconnects/hr; with continuous traffic where connections are never idle, configure 1 reconnect/hr (only pod restarts and deployments matter).

Local signature verification (recommended): the gRPC server validates the JWT cryptographic signature locally using the authorisation server's public key. Zero extra requests per gRPC call. The only extra calls are periodic token acquisitions.
Remote introspection (RFC 7662): the server calls the authorisation server for every incoming gRPC request to verify the token is still active. This doubles outbound request volume. Use only when real-time revocation checking is a hard requirement.

Unary interceptor: validates the JWT on every individual RPC call. Suitable for request/response APIs where each call is independent.
Stream interceptor: validates once at stream open and covers all messages within that stream lifetime. Lower per-message cost for long-lived bidirectional or server-streaming RPCs.
Sends Authorization: Basic base64(username:password) in every request header (50–100 bytes per request). No extra requests are generated, but the credential is valid until the password is changed — there is no expiry, no rotation, and no revocation mechanism short of a password reset. Use only for internal tooling or local development. For production, prefer OAuth 2.0 + JWT which provides time-bounded, revocable, fine-grained access control per RFC 6749.
